# @forge/ops

The operation vocabularies of Forge: 388 ops in 164 vocabularies, written in FL (the Forth-like Forge language), plus the build-time catalogue and the loaders that make them available in Node and in the browser.

The package holds:

- `vocab/` the FL sources (`.fth`) and their test vectors (`.test.json`);
- `src/prims/` the few TypeScript primitives that FL cannot replace;
- `src/` the loaders (Node fs provider and Vite `import.meta.glob`), the dependency scan, and the catalogue builder;
- `dist/catalogue.json` the catalogue, derived from the vocabularies at build time (`npm run build`). Nothing is registered by hand.

## Layout per vocabulary

For a vocabulary `<v>`:

| File                  | Holds                                                                          |
| --------------------- | ------------------------------------------------------------------------------ |
| `vocab/<v>.fth`       | the words, with their stack-effect headers and `META:` blocks                  |
| `vocab/<v>.test.json` | the op test vectors (schema: `vocab/vectors.schema.json`, spec: RECIPES.md §9) |
| `src/prims/<v>.ts`    | optional: primitives, only when FL cannot do the job (see below)               |
| `src/<v>.test.ts`     | tests of the FL vocabulary                                                     |

Every `.fth` file starts with the one-line licence comment `\ Copyright 2026 Darkcollective, LLC. Licensed under the Apache License, Version 2.0.` (a comment, so nothing reads it, and no check enforces it).

`src/prims/` holds only primitive modules and their tests (`src/prims/<v>.test.ts`). Tests of FL vocabularies go in `src/<v>.test.ts`. The package tests derive the vocabulary list from disk, so a new vocabulary is picked up without registering it. A qualified `see-also` counts as a load dependency, as does `USING:`.

## FL first

Ops are written in FL wherever feasible. A TypeScript primitive is allowed only when the core cannot express something (the core has no logarithm, so `analysis:_log2` is a primitive) or when FL is too slow on realistic input, measured at 64 KiB. Then the primitive is a minimal private `_helper`, and the op logic and metadata stay in FL.

The private primitives, each in `src/prims/<v>.ts`:

- `analysis:_log2`: the logarithm the core lacks;
- `charset:_decode`: the WHATWG decoder for an encoding label;
- `cobs:_starts`: the offsets of the blocks of COBS data;
- `float:_pack` and `float:_unpack`: decimal text to and from IEEE 754 bytes;
- `distance:_levenshtein`: the weighted edit distance of two texts over code points (a dynamic programme of length times length cells, which needs a fast mutable array that FL lacks; limited to 100 million cells);
- `unicode:_normalize`: Unicode normalisation (NFC, NFD, NFKC, NFKD);
- `coords:_math` and `coords:_atan2`: the trigonometric and hyperbolic functions (sin, cos, tan, asin, atan, sinh, cosh, asinh, atanh) and atan2 that the core lacks, for the UTM projection and the haversine distance; the series, the zones and the formats are FL;
- `datetime:_zone-offset`, `datetime:_zone-abbr` and `datetime:_zones`: the host's time zone rules over `Intl` (the offset of an IANA zone from UTC in seconds at an instant, its short name, and the list of zone names, with UTC); the calendar maths, the moment.js-style format tokens, the parser and the operations are FL;
- `aes:_check-key`, `aes:_block-enc`, `aes:_block-dec`, `aes:_crypt` and `aes:_gcm`: AES over the audited `@noble/ciphers` (the block pair also drives `blockmode` for OFB); `aes-kw:_wrap` and `aes-kw:_unwrap`: RFC 3394 key wrap over noble's `aeskw`; `chacha:_crypt`, `salsa20:_crypt` and `xsalsa20:_crypt`: the stream ciphers over noble;
- the block ciphers without an audited library, each a private single-block pair and a key check, written from the specification: `des`, `triple-des`, `blowfish`, `rc2`, `rc6`, `twofish`, `sm4`, `tea`, `xtea` and `present` have `_check-key`, `_encrypt-block` and `_decrypt-block`; `gost28147` has the same three plus `_crypt-ext` (the whole-message modes with CryptoPro key meshing, which cannot be a block quotation because the key changes between blocks), `_wrap` and `_unwrap` (RFC 4357 key wrap and its IMIT); every mode and the padding come from `blockmode`;
- `rc4:_crypt`, `ciphersaber2:_crypt` and `rabbit:_crypt`: the stream ciphers, whose state loops need a fast mutable array that FL lacks (the same reason as `sigaba:_run`); `xxtea:_encrypt` and `xxtea:_decrypt`: XXTEA, a variable-length block cipher that does not use `blockmode`;
- `cmac:_mac` (the CMAC of SP 800-38B over the AES and Triple DES block functions called from TypeScript, because the block words of those vocabularies are private), `lmhash:_hash` (the DES work of the LM hash over `des.ts`), `ascon:_hash`, `ascon:_mac` and `ascon:_aead` (Ascon-Hash256, the Ascon-Mac of the designers' reference code and Ascon-AEAD128, from the specification), and `bcrypt:_hash`, `bcrypt:_verify`, `bcrypt:_parse` (the Blowfish-based hash is slow by design, far beyond the FL step budget; the cost is capped, see `src/prims/bcrypt.ts`);
- `pbkdf2:_derive`, `scrypt:_derive`, `argon2:_derive` and `argon2:_verify`: the key derivation functions over the audited `@noble/hashes` (they are memory- or time-hard, far beyond the FL step budget; each caps its cost, see the vocabulary's primitive file; the Argon2 primitive also writes and parses the PHC encoded string). HKDF and EVP_BytesToKey are plain FL, over `hmac:digest` and the md5, sha1 and sha2 digest words.
- No private clock or random primitives remain. The clock (`+time`) and the host CSPRNG (`+random`), which FL cannot read, are read in one place each, the shared `clock` and `random` vocabularies. **The effects pattern:** a public word that needs the time or random bytes calls `clock:now-s`, `clock:now-ms`, `random:bytes-of`, `random:below` or `random:between` (`fernet:encrypt` is `key 16 random:bytes-of clock:now-s _seal`), and the compiler infers the `+time` and `+random` effects of the public word from them. The constructions (`fernet:_seal`, `fernet:_open`, `flask-session:_sign`) take the time and the IV as arguments, so tests pin them, and the public words only supply them. The wave 4 private primitives (`fernet:_now`, `fernet:_random-iv`, `flask-session:_now`, `ciphersaber2:_random-iv`, `bcrypt:_random-salt`) were removed in the wave 5 close-out. A host with no `crypto.getRandomValues` is `E_PRIMITIVE`, never a fall-back to `Math.random`.
- `random:bytes-of`, `random:below`, `clock:now-ms`, `list:sort`, `list:sort-by` and `list:shuffle`: the **shared** words of wave 5, public (no leading underscore) because other vocabularies call them qualified. `random:bytes-of ( n -- bytes )` and `random:below ( n -- int )` read the host CSPRNG (`+random`); `clock:now-ms ( -- int )` reads the host clock (`+time`); `list:sort ( list -- list )`, `list:sort-by ( items keys -- list )` and `list:shuffle ( list -- list )` are the stable sort and the Fisher-Yates shuffle that the core lacks (sorting 65,536 strings in FL would cost far more than the step budget; the shuffle is `+random`). `random:between` and `clock:now-s` are FL over them. See "Wave 5 conventions".
- `json:parse`, `json:stringify`, `json:null` and `json:null?`: the **shared** JSON reader and writer (RFC 8259) between JSON text and FL values, public because other vocabularies call them qualified (`json` is internal, so none is a catalogue op). A bare FL loop over the 65,535 code points of a 64 KiB text costs 358,523 VM steps (5.5 a character) before it keeps any state, and a scanner with strings, escapes, numbers and nesting costs several times that; the primitives parse or write 64 KiB in 2 VM steps and about 10 ms. `json:compact` and `json:pretty` are FL over `stringify`. See "JSON values (WP 5.48)".
- `csv:_parse` and `csv:_write`: the RFC 4180 scanner and writer behind `csv:to-json` and `csv:from-json` (quotes, doubled quotes and delimiters inside quoted cells are a per-character state machine, too slow in FL at 64 KiB). The delimiters, the header rules, the mapping between rows and JSON values and every check are FL.
- `diff:_edits`: the edit script between two lists of strings (Myers' O(ND) difference in linear space, capped in work), as runs of equal, deleted and inserted tokens. FL has no mutable arrays, so the furthest-reaching vectors of the algorithm cannot be kept in FL; the tokens, keys, hunks and text of `diff:compare` are FL.
- `bzip2:_compress` and `bzip2:_decompress`: the bzip2 codec written from the format (BWT by prefix doubling, MTF, Huffman, the MSB-first CRC-32, whose table is `msbTable` of `src/prims/crc.ts`): the bit-level loops and the per-byte CRC are far too slow in FL. `_decompress ( data verify -- bytes )` stops at the value limit; the parameters and range checks are FL.
- `deflate:_deflate` and `deflate:_inflate`: raw DEFLATE (RFC 1951) over `fflate`: the entropy coding (LZ77 and Huffman) is far too slow in FL at 64 KiB. `_inflate ( data start -- bytes end )` also returns where the stream ended, so the zlib and gzip trailers are read in FL, and it stops at the value limit (see "Wave 6 conventions"). Level 0 writes the stored blocks itself (fflate 0.8.3 appends a second, empty, final block at multiples of 65,535 bytes: found by the wave 6 cross-check). The zlib and gzip framing, the checksums (`adler32:checksum`, `crc:checksum`) and the parameters are FL.
- `lzma:_compress` and `lzma:_decode`: the `.lzma` (LZMA alone) codec over `lzma1` (synchronous, pure ESM): the match finder and the range coder are far too slow in FL. `_decode ( data -- bytes int )` also gives the size the header declares (-1 when unknown), and the decoder never gets a stream that can pass the value limit: a declared size over it is refused, and an unknown size is declared as the limit plus one (see "Wave 6 conventions" and `src/prims/lzma.ts`). The 13-byte header check and the size comparison are FL.
- `lznt1:_decompress`: the LZNT1 decompressor (MS-XCA 2.5, written from the specification). An FL prototype of the chunk and flag-group loop decoded 64 KiB correctly (1.0 to 3.2 million VM steps, 0.1 to 0.3 s) but costs 12 to 49 steps per output byte, which caps the output near 200 KB under the default step limit and near 100 KB for an untrusted recipe, far below the 16 MiB value limit; it stops at the value limit (see "Wave 6 conventions").
- `xpress:_lz77` and `xpress:_huffman`: the XPRESS Plain LZ77 and LZ77+Huffman decompressors (MS-XCA 2.4 and 2.2, written from the specification): per-byte match loops (the same cap as LZNT1) and, for the Huffman form, bit-level canonical decoding with a 2^15-entry table. Both stop at the value limit, and a match length of up to 2^32 allocates nothing.
- `lz4:_xxh32`, `lz4:_blocks`, `lz4:_legacy` and `lz4:_encode`: the LZ4 block coder and XXH32 written from the specification (no library): a decoder bounded by the value limit that checks block checksums, and a greedy hash-chain encoder, because per-byte loops are far too slow in FL; the frame (magic numbers, FLG and BD, content size, header and content checksums, concatenated, skippable and legacy frames) is FL;
- `lzstring:_compress` and `lzstring:_decompress`: lz-string 1.5.0 behind a format choice (default as UCS-2 big-endian bytes, utf16, base64, uri); decompression first replays the token structure with lengths only (`measure`) to stop at the value limit before the library builds any string;
- `zstd:_decompress`: Zstandard (RFC 8878) decompression over `fzstd`. The frames are walked here (the dictionary ID, the window and the declared size are checked, and the XXH64 content checksum is computed and compared, which fzstd does not do); fzstd decodes each frame in chunks into a bounded output. Justified: fzstd exposes no frame boundaries and no checksum, and the 64-bit hash is BigInt (16 MiB in about 0.3 s). The FL word is `zstd:decompress`.
- `crc:_crc` and `adler32:_adler`: the per-byte loops of the checksums, shared by every container (`deflate` zlib and gzip, `zip`; `bzip2` shares the MSB-first CRC table, `generate-all:_crcs` the loop). `_crc ( data width poly init refin refout xorout -- int )` is the table-driven CRC of the Rocksoft model for any width from 1 to 82 (numbers up to 32 bits, BigInt above); `_adler ( data -- int )` is Adler-32 in blocks of 5552 bytes. In FL the loops cost about 13 VM steps a byte (and Adler-32 a list of 16 bytes per byte), which capped an input near 750,000 bytes; with the primitives `crc:checksum` is 130 VM steps and `adler32:checksum` a few dozen for any length (16 MiB in 0.1 s). The parameters, the preset table, the checks, the metadata and the formatting are FL.
- `zip:_cd-offsets` and `zip:_extract`: the walk over the central directory entries (each offset depends on the lengths of the one before; growing the list in FL is quadratic: 10,000 entries took 27 s) and the inflation of several entries under one output budget (`maxValueBytes` for the sum of all entries, carried from one entry to the next, which FL cannot do without a quadratic list). The ZIP container (local headers, central directory, end record, DOS time, flags, checks) is FL.
- `tar:_headers`, `tar:_oct` and `tar:_sum`: the walk over the headers of a tar archive (quadratic in FL: 12,000 entries took over 30 s), an octal header field (250 VM steps in FL, six per header) and the byte sum of the header checksum (2,500 steps in FL). Reading costs about 400 VM steps per entry. The tar format itself (fields, names, long names, writing) is FL.
- `asn1:parse-in`, `asn1:oid-decode`, `asn1:oid-encode`, `asn1:oid-name`, `asn1:oid-short`, `asn1:oid-find`, `asn1:_string` and `asn1:_pem-scan`: the shared ASN.1 layer of wave 7 (the DER reader as a recursive descent that builds a record per element, bounded by depth and by the value limit; the object identifier codec, whose arcs can exceed 2^53; the table of about 250 OID names, which FL cannot hold as a constant; the PEM block scanner; the character sets of the ASN.1 string types). Everything else in `asn1`, `asn1-dump`, `oid` and `pem` is FL. The public ones are shared words: see "Wave 7 conventions".
- `rsa:_prime`: the prime search of RSA key generation (`_prime ( pool bits bases -- int )`: the first probable prime of `bits` bits among the candidates cut from a pool of random bytes that FL supplies from `random:bytes-of`, or 0; trial division by the primes below 65536, a Fermat test to base 2 by squarings, then Miller-Rabin with base 2 and 12 random bases). The core `powmod` does the RSA operations (27 ms for a 2048-bit exponentiation); the FL search of `prime:generate` took 2.3 s on average per 2048-bit prime, so a 4096-bit key would average 4.6 s with a tail past the 30 s limit; the primitive makes it 1.8 s on average (slowest of twelve runs 3.4 s). The primitive reads no random source. See "RSA (WP 5.50)".

- `ecdsa:_size`, `ecdsa:_seed-length`, `ecdsa:_keygen`, `ecdsa:_public-key`, `ecdsa:_valid-point`, `ecdsa:_uncompressed`, `ecdsa:_sign` and `ecdsa:_verify`: ECDSA over `@noble/curves` (P-256, P-384, P-521, secp256k1), the point arithmetic and RFC 6979 of the key pair, signature and verification words (a 521-bit scalar multiplication is far beyond the FL step budget). The digest, the PEM and DER keys, the signature formats and the random seed are FL. See "Wave 7 conventions".
- `sm2:_order`, `sm2:_mul-base`, `sm2:_mul` and `sm2:_valid-point`: the SM2 curve (GB/T 32918.5) over `@noble/curves`' generic Weierstrass curve; SM3, the KDF, the layouts and the random k are FL.
- `gost3410:_size`, `gost3410:_order`, `gost3410:_public-key`, `gost3410:_sign` and `gost3410:_verify`: GOST R 34.10-2012 (RFC 7091) on the same generic curve (it is not ECDSA); Streebog, the choice of k and the retry are FL.
- `gost-mac:_imit`: the GOST 28147-89 IMIT with a MAC of 1 to 8 bytes (the 16-round loop per block is far too slow in FL at 64 KiB; 64 KiB is 300 steps). It keeps a copy of the S-box tables of `gost28147` (whose block cipher is private to its file); `src/gost-mac.test.ts` checks the two agree for all eight S-boxes.
- `sigaba:_run`: the SIGABA rotor stack over letters 0 to 25 (the loop needs a fast mutable array, which FL lacks);
- `classical:_ls47`: the LS47 letter-by-letter cipher on a given board, for the same reason;
- `bombe:_search`: the Bombe test over the 17,576 start positions of one rotor order;
- the hashing primitives, one per digest vocabulary and always `_hash` (`sha2:_hash`, `md6:_hash`, `snefru:_hash`, and so on; BLAKE2, BLAKE3, Keccak, SHA-3, SHAKE, SHA-1, MD5, RIPEMD-160 over `@noble/hashes`, the others written from their specifications), plus `ssdeep:_pieces` (one pass of the rolling hash) and `generate-all:_crcs` (many CRC presets at once, for speed only; see "Justified exceptions").

The public primitives are the `hex`, `base64` and `regex` words and `raise:coerce` and `raise:range`.

FL's own `fail` raises only `E_USER`. Typed errors come from the internal `raise` vocabulary:

- `raise:coerce ( reason:str -- )` raises `E_COERCE`, for data that cannot be decoded;
- `raise:range ( reason:str -- )` raises `E_RANGE`, for a bad argument.

Use it with `USING: raise` or the qualified names. The words have no outputs, so they are not catalogue ops.

**Rule: check `util` before writing a helper. Anything more than one vocabulary needs goes in `util`.**

When work packages run in parallel, an agent cannot edit `util.fth` (the orchestrator owns it), so it may need a private copy of a helper for the length of its package. The rules for that:

1. Keep a **straight copy** of the helper in your own vocabulary, with the body you would have put in `util`. **Never vary the body to avoid the sweep**: do not reorder the words, swap an operand test (`j d len <` for `j d len >=`), change a constant into a computed one or otherwise write the same function differently. A disguised copy is a defect, and the structural check below reports it anyway.
2. Put the comment line `\ util-candidate: <proposed util name>` **immediately before** the definition (no blank line between).
3. List the helper in your report as a **utility candidate**: proposed name, stack effect, why, and the vocabularies that have the same need.
4. The orchestrator promotes every marked helper into `util` at the wave close-out, deletes the copies and the markers, and the final state has no marker left.

Example:

```forth
\ util-candidate: strip-space
: _clean ( s:str -- str )
  s str>codes [ util:space? not ] filter codes>str ;
```

### Finding copies: the dupes test and `npm run dupes`

`src/dupes.ts` (not exported from the package, so not in the browser bundle) reads every `vocab/*.fth`, extracts each colon definition and normalises its body: comments, the `doc` and `category` lines are dropped, input names become positional placeholders (`b 32 =` equals `code 32 =`), and words of the same vocabulary are qualified so two private helpers with the same name are not confused. Four reports:

- **Exact duplicates**: definitions in different vocabularies with the same input and output types and identical normalised bodies. `src/dupes.test.ts` **fails** on any, naming the words; move the helper into `vocab/util.fth`. A group whose copies **all** carry a `util-candidate` marker is not an exact duplicate but a pending promotion (next).
- **Pending util promotion**: exact-duplicate groups where every copy has the marker `\ util-candidate: <name>` right before it, listed by proposed name. Not a failure while a wave is running. One unmarked copy in the group makes the whole group a failure. `src/dupes.test.ts` also checks that **none is left** in the repository, so the close-out cannot forget them.
- **Near duplicates**: pairs in different vocabularies with the same input and output arity and a Jaccard similarity of at least 0.8 over token bigrams. Bodies under 4 tokens are ignored.
- **Likely re-implementations**: private (`_`) helpers in different vocabularies with the **same effect signature** (input and output types) and the **same set of core words** (every word of the body that is not a parameter or defined in its own vocabulary, qualified words included; order and repetition ignored; at least 3 distinct words). This catches the same function written with a different body. Near duplicates and likely re-implementations never fail a test: look at each at the close-out, and either promote the helper or write down why the two are different (for example `classical:_atbash-code` reflects a letter, `morse:_upper-cp` folds case; they only look alike).

`npm run dupes -w @forge/ops` builds the package and prints all four reports (always exits 0). Run it when reviewing a work package. At a wave close-out the target is 0 exact duplicates, 0 pending promotions, and every remaining near duplicate or likely re-implementation resolved or justified.

### Justified exceptions

The sweep reports copies that a promotion would remove. A pair it reports and that stays is written down here, and the private helper carries a one-line comment saying why. Pairs the sweep never sees (an exact copy whose body calls a private helper of its own vocabulary, so the normalised bodies differ) are listed as well.

- `enigma:_step` and `typex:_step` implement the same Enigma-style stepping with the double step, and `typex:_turn` only names the row-offset update. They stay separate: the rotor state is in each vocabulary's `VARIABLE`s (`_b1`, `_b2`, `_b3`, `_NR`, `_NM`), so a shared util word would have to take five values and give back three on every key press. That costs more VM steps on the per-letter path than the inline test and update. The sweep does not report the pair for the reason above.
- `enigma:_byte` and `typex:_byte` have the same core words. Each reads its own `_LT` table and its own `_press` on the per-letter path, so the call cannot be shared.
- `classical:_atbash-code` and `morse:_upper-cp` reflect a letter within its case and fold a lower-case letter to upper case. They only look alike.
- `classical:_text-printable?`, `string-escape:_space?` and `url:_unreserved?` test three different sets of code points (printable ASCII, the Unicode spaces that the minimal escape level writes, and the unreserved URL characters).
- `base32:_ungroups` and `classical:_cb-enc` map a helper over an index range and join, over different per-group words.
- `fractionating:_adf-labels` and `polygraphic:_pl-alpha` each pick one of two unrelated literals by a name.
- `luhn:_value` turns the code of a digit or letter into its value in a radix (0 to 9, then a to z, either case), like `classical:_atbash-code` and `morse:_upper-cp` it maps a code through two or three range tests, and only looks alike.
- `blake2b:digest` and `blake2s:digest` (and the other thin hash words, such as `sha3:digest` and `keccak:digest`) have bodies of one call, `size key _hash`, which is under the sweep's four-token threshold, so the sweep never compares them. Judged here: not a duplication worth sharing. The call is to the vocabulary's own private `_hash`, which a private word cannot share across vocabularies; the two primitives (`src/prims/blake2b.ts` and `blake2s.ts`) differ in the library function, the size and key limits (64 and 32 bytes) and the messages, and sharing them would only turn those four things into parameters of a factory. CyberChef also has two operations. The pattern is the `sha2` template of "Hashing conventions".
- `jwt:_need-key` and `flask-session:_need-key` both raise `E_RANGE` for an empty key. They differ in their message (the JWT key, the Flask secret key, which CyberChef words as "Secret key required"), so one util word would need the message as a parameter and every call would pass a literal, which is longer than the three-token body. Kept separate.
- `generate-all:_crcs` runs the 171 presets in one primitive call. Since the close-out it no longer holds a second copy of the CRC model: it calls the loop of `crc:_crc` (`crcRegister` in `src/prims/crc.ts`). What it still saves is the per-preset cost of calling `crc:checksum` 171 times from FL (each call parses the preset table and formats its result, about 130 VM steps and one pass over the data, against one call here that also computes presets with equal parameters once). With the checksum primitive an FL loop over the presets would now fit the step limit, so the primitive is no longer needed for the step budget, only for the single pass and the shared cache; it can be replaced by FL if the report ever has to shrink. `src/generate-all.test.ts` holds it equal to `crc:checksum` for every preset on random inputs. The preset table is shared as `util:crc-presets`.
- `case:_body` and `hexdump:_uncolon` share the core words of "cut the first or last character off a string when a test holds". The tests (a leading `[` or `[^`, a trailing colon) and the cuts are different, so a util word would be a conditional slice parameterised by a test and two offsets, longer than either body.
- The wave 5 close-out promoted its duplicates instead: `util:contains?` (was `case:_has` and `coords:_has?`), `util:total-text` (`datetime:_total-text` and `extract:_render`), `util:round-div` (`units:_round-div` and `coords:_pico2`, which agree on every input), `util:match-texts` (the `regex:find-all [ "text" get ] map` idiom of `case`, `datetime`, `diff`, `extract` and `rake`), `list:unique` (`extract:_unique`, `datetime:_distinct` and `set:_unique`), `util:civil-from-days`, `util:days-from-civil` and `util:iso-from-ms` (the Hinnant calendar of `datetime`, `objectid` and `uuid`), `util:zero-pad`, `util:ordinal-suffix` and `util:tdiv` (from `datetime`), and `util:str-chunks` (now linear, so `lines:wrap` uses it).
- Helpers kept private on purpose after the wave 3 review (one user each): `fletcher:_weighted` (it weighs by `n - i div s`; Adler-32 is now a primitive), and `hmac:_pad`.

## Hashing conventions

The hashing vocabularies (wave 3) follow the `sha2` vocabulary, which is the template.

- **Bytes out.** A digest word returns the raw digest as `bytes`, never hex text. Chain `hex:encode` for text. The category is `Hashing`.
- **Naming.** One vocabulary per family (`sha2`, `sha3`, `blake2`, `md5`, `crc`, ...), lower-kebab-case. The public word of a hash is `digest`, with a parameter for the variants (`sha2:digest` takes `size:choice{"224"|"256"|"384"|"512"|"512/224"|"512/256"}`). Where CyberChef has a variant parameter, use one parameterised word, not one word per variant. Checksums (crc, adler-32, fletcher, ...) are written in FL, not primitives.
- **Library, not WebCrypto.** Hashes that `@noble/hashes` (audited, MIT, pinned to an exact version) covers use it, and all hash primitives are synchronous. Import only the subpath you need (`@noble/hashes/sha2.js`) so the vocabulary's lazy chunk stays small; the chunk is loaded only when the vocabulary is used and does not count against the first-paint budget.
- **Wrapping a noble function.** Follow `src/prims/sha2.ts`: one private primitive `_hash ( data:bytes <variant>:str -- bytes )` that looks the variant up in a table (with `Object.hasOwn`, so `toString` is not a variant) and raises `E_RANGE` through `rangeFailure` for an unknown one. The primitive does nothing else. The public word, its doc string, category, `choice{}` parameter, defaults and `META:` stay in `vocab/<v>.fth`. Own the tests: `src/prims/<v>.test.ts` for the primitive and `src/<v>.test.ts` for the word through the runtime.
- **Vectors.** `vocab/<v>.test.json` takes its vectors from the official specification or an RFC (FIPS 180-4, FIPS 202, RFC 1321, RFC 7693, RFC 2104, ...), and `ref` cites it. CyberChef is only a throwaway cross-check oracle: never copy its tables or outputs into the repository. Include the empty input, the standard short and long messages, and a 64 KiB test inside the default limits (against `node:crypto` where it has the algorithm).
- **HMAC** is its own vocabulary (`hmac`), taking the hash name and the key as parameters, not a parameter of each hash.
- **Defaults follow CyberChef's** where the choice is arbitrary (SHA-2, SHA-3 and Keccak 512, SHAKE256 with 64 bytes, RIPEMD 320, MD6 256 bits with 64 levels, Snefru 128 bits with 8 passes, BLAKE2b 64 and BLAKE2s 32 bytes), so a recipe moved from CyberChef gives the same digest. A default stays Forge's own where the standard names one (BLAKE3 gives 32 bytes, its specification's output size; GOST uses the CryptoPro S-box of the standard, not CyberChef's E-TEST cipher set). Sizes are in bytes (SHAKE length, BLAKE2 size) where CyberChef counts bits; the coverage rows say so.
- **Reports.** `generate-all` builds a text report from the digest and checksum words, one algorithm per line with its hex. It is its own vocabulary because it depends on thirty hash vocabularies and `hash-analysis` must stay light. Its `length` and `names` parameters are CyberChef's.
- **Not here, in wave 4.** CMAC (`cmac`), the LM hash (`lmhash`), bcrypt (`bcrypt`), Argon2 (`argon2`) and Ascon (`ascon`) need AES or DES, or are key derivation functions, so they came with the ciphers: see "Cipher conventions". They follow the digest-word shape (raw bytes out, `key` parameters, `E_RANGE` for a bad key) where they hash or authenticate.

## Cipher conventions

The symmetric cipher vocabularies (wave 4) follow the `aes` vocabulary, which is the template, as the hashing vocabularies follow `sha2`.

- **Data.** Bytes in, bytes out. The ciphertext is raw bytes (chain `hex:encode` or `base64:encode`), and the plaintext of a decryption is raw bytes. CyberChef's Input and Output encoding menus are chain steps here.
- **Key and IV.** `key`-type parameters (`key:key{hex|utf8|latin1|base64}`), so a recipe or the UI gets all four encodings for free, and the word receives bytes. The key has no length constraint in its header, because a header constraint raises `E_PARAM_INVALID`; the word checks the length and raises `E_RANGE` (see "Errors"). The IV (or nonce) is a second `key` parameter, empty by default, which is right for ECB and for the ciphers that take none.
- **Empty IV.** An empty IV is an error for the ciphers that follow the shared convention (E_RANGE), but TEA, XTEA, RC6 and GOST 28147-89 treat it as zero bytes, as CyberChef does; that default is `util:iv-or-zeros ( iv n -- bytes )`.
- **Mode.** A `choice` parameter (`mode:choice{CBC|CFB|OFB|CTR|GCM|ECB}="CBC"`), with CyberChef's names and its default (CBC). A cipher offers the subset it has. A mode that does not use an IV ignores it.
- **Padding is a separate parameter**, `padding:choice{pkcs7|none}="pkcs7"`, not a mode variant. CyberChef's NoPadding variants (CBC/NoPadding, ECB/NoPadding) are the same mode with padding switched off, and folding them into the mode would double the mode list for every cipher and make the shared layer match on mode names. A separate parameter keeps each mode word one thing. Padding is PKCS#7 (RFC 5652 section 6.3): `n` bytes of the value `n`, `n` from 1 to the block size, so whole input gets a full extra block. It applies to ECB and CBC only; CFB, OFB, CTR and GCM keep the length and ignore the parameter. With `none`, ECB and CBC need whole blocks.
- **Errors.** `E_RANGE` is for an argument with a bad value: a key of a length the cipher does not take, an IV of the wrong length (for the modes that use one), an unknown mode. `E_COERCE` is for data that cannot be processed: bad PKCS#7 padding (usually a wrong key or IV), ciphertext that is not whole blocks where the mode needs them (and any input with padding off that is not), and a GCM tag that does not verify or an input shorter than the tag. A decryption that fails returns no plaintext. A key length is checked even for an empty input.
- **GCM.** The 16-byte tag is **appended to the ciphertext** by encryption, and decryption takes the last 16 bytes as the tag and verifies it before it returns anything, raising `E_COERCE` otherwise. There is no tag-length parameter (the tag is the full 128 bits; truncated tags are a known weak spot, and `@noble/ciphers` does not offer them). The additional authenticated data is a `key` parameter `aad`, empty by default, and it must be the same on both sides. The IV is at least 8 bytes (the library's lower limit), 12 recommended. This differs from CyberChef, whose GCM tag is a separate output of encryption and a separate parameter of decryption: a single byte string is what a chain of words can carry, and it is what most libraries produce.
- **CTR and CFB.** NIST SP 800-38A leaves the counter's incrementing function to the application, so the ciphers differ, and each follows CyberChef's convention for its counterpart, found by the cross-check of WP 5.29. AES, DES, Triple DES, Blowfish and SM4 add one to the **last four bytes** of the counter block, modulo 2^32, with no carry into the rest (node-forge's inc32: `blockmode` mode `CTR32`; for AES the primitive does it, cutting the data where the low word wraps); Twofish and RC6 read the whole block as a **little-endian** integer, first byte least significant (mode `CTRLE`); TEA, XTEA and the other users of plain `CTR` increment the whole block as one big-endian integer; GOST 28147-89 uses its own gamma. A counter that does not wrap gives the same key stream under all of them, so the SP 800-38A and OpenSSL vectors agree. A cipher word turns its CTR mode into the right one with `blockmode:ctr-as`. CFB is full-block CFB (CFB-128 for AES). OFB is standard output feedback.
- **Vectors.** From the standard: NIST SP 800-38A appendix F for the modes, FIPS 197 for the block, the GCM specification (McGrew and Viega) or NIST SP 800-38D for GCM, RFCs where there are some (RFC 3602), and `ref` cites the example. Include the empty input, a short input that is not a block multiple, errors for each case of "Errors", and a 64 KiB input in every mode against `node:crypto` (where it has the cipher).

### The block-cipher architecture

AES, ChaCha and the key wraps are covered by the audited `@noble/ciphers` and may use its own modes for speed. DES, Triple DES, Blowfish, RC2, RC6, Twofish, SM4, TEA, XTEA, PRESENT and GOST 28147-89 have no audited library, so they are Forge's own primitives, written from their specifications. Each such cipher is:

- a **private single-block primitive pair**, `_encrypt-block` and `_decrypt-block`, each `( block:bytes key:bytes -- bytes )`, in `src/prims/<v>.ts`, with the key schedule inside (a cipher may cache the schedule of the last key it saw, since the key is the same for every block of a call);
- **no modes of its own.** Every mode and PKCS#7 padding come from the one shared vocabulary `blockmode`, so the modes are written once and cannot drift apart.

`blockmode` (`vocab/blockmode.fth`, internal, in `INTERNAL_VOCABS`) is written in FL and takes the block function as a **quotation** that closes over the key. Its two words:

```
blockmode:encrypt ( data:bytes mode:str iv:bytes bs:int padding:bool enc:quot -- bytes )
blockmode:decrypt ( data:bytes mode:str iv:bytes bs:int padding:bool enc:quot dec:quot -- bytes )
```

`mode` is `ECB`, `CBC`, `CFB`, `OFB` or `CTR` (and the counter variants `CTR32` and `CTRLE`, below); `bs` is the block size in bytes, **any size**: the layer never assumes 8 or 16 (RC6 has 4-byte blocks at word-size 8, `rc6:encrypt` with `word-size` 8, and 32-byte ones at 64); `enc` and `dec` have the effect `( block:bytes -- bytes )` and handle one block. Decryption takes both quotations because ECB and CBC decrypt with `dec` while CFB, OFB and CTR run the cipher forwards with `enc`. `blockmode:pad` and `blockmode:unpad` (`( data:bytes bs:int -- bytes )`) are PKCS#7 on their own. A cipher word for an 8-byte block cipher looks like this (the cipher checks its key length in `_encrypt-block`, or in a `_check-key` of its own; `padding "pkcs7" =` turns the choice into the boolean):

```
: encrypt ( bytes key:key{hex|utf8|latin1|base64} iv:key{hex|utf8|latin1|base64}="" mode:choice{CBC|ECB}="CBC" padding:choice{pkcs7|none}="pkcs7" -- bytes )
  mode iv 8 padding "pkcs7" = [ key _encrypt-block ] blockmode:encrypt ;
```

The block function is a quotation, so the key schedule is whatever the primitive does per call; a primitive that expands the key on every call (as `aes:_block-enc` does) is fine for the sizes here, and one that caches the last key is faster. The block quotations are called once per block, and the layer checks the IV length (`E_RANGE`), the mode name (`E_RANGE`), whole blocks and padding (`E_COERCE`).

**Why FL.** FL first applies (see above). The layer was measured driving a block primitive at 64 KiB: a CBC encryption through `blockmode:encrypt` takes about 98,500 VM steps (CBC decryption 103 thousand, ECB 70 thousand, CFB and OFB 98 thousand, CTR 1.07 million for its counter arithmetic), against the default limit of 10 million and the untrusted bake budget of 5 million. The loops use `map` over the list of blocks and one `VARIABLE` for the chaining value, so they are linear in the length. The layer is therefore FL, and only the block primitives are TypeScript. `src/blockmode.test.ts` drives it with a trivial XOR block cipher (known answers by hand) and with raw AES blocks, and holds the result byte-identical to noble's own ECB, CBC, CFB and CTR and to `aes:encrypt`; AES uses the layer itself for OFB, which noble lacks.

A pitfall for FL authors: do not write `USING: raise` in a vocabulary that also uses the core word `range`, because `raise:range` would then hide it. Call the raise words qualified (`raise:range`, `raise:coerce`).

## Wave 5 conventions

Wave 5 (utils, extractors, date and time, arithmetic, generators, language) adds many small ops that read and write text. These rules keep them alike; WP 5.30 built the shared words they use.

- **Line and list ops are `str` in, `str` out.** The data is the text as it is (UTF-8), a list is that text cut at a delimiter, and the result is joined with a delimiter again. Do not return an FL `list` from an op (a list is not a UI type). Splitting is `data delimiter util:delimiter split`, joining is `list delimiter util:delimiter join`. Take care that `split` raises on an empty delimiter: a word that splits must refuse the `none` choice (`E_RANGE`, say "needs a delimiter") or define what splitting at "none" means (every character) and say so in its doc.
- **The delimiter parameter.** Copy this header form exactly, with the choices in this order, so the UI shows one list everywhere; an op may take a subset (say so in its doc) and picks its own default:

  ```forth
  : sort ( data:str delimiter:choice{space|comma|semicolon|colon|newline|crlf|cr|tab|none}="newline" -- str )
  ```

  `util:delimiter ( choice:str -- str )` turns a choice into its text: `space` is one space, `comma` `,`, `semicolon` `;`, `colon` `:`, `newline` a line feed (U+000A; CyberChef calls it "Line feed"), `crlf` a carriage return and a line feed, `cr` a lone carriage return, `tab` a tab and `none` the empty string. Anything else is `E_RANGE` (a header `choice` already rejects it before the word runs (`E_RECIPE_INVALID` in a recipe, `E_PARAM_INVALID` at a direct call); the check is for words called from FL). The older `util:separator` stays for the vocabularies that use it (it answers space for any unknown choice); new code uses `util:delimiter`.

- **Where the delimiter is a free text** (CyberChef's "Delimiter" boxes that take any string), use a `str` parameter and say so; do not add choices to the list above.
- **Numbers in text.** An integer is written as plain decimal digits with a `-` for negatives and no separators (`int>str`), and read back with `str>int` (an optional sign, digits only; surrounding spaces are trimmed first by the op). Big integers are first class; a result of ops on them must not pass through `num`. An op that reads a list of numbers raises `E_COERCE` on a piece that is not a number, naming the piece; it does not skip it.
- **Using the shared words.** Call them qualified or with `USING:`; they are internal vocabularies, so your vocabulary may use them and nothing else has to register them:

  | Word              | Stack effect                       | Meaning                                                                                                                                              |
  | ----------------- | ---------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
  | `random:bytes-of` | `( n:int -- bytes )`               | n random bytes from the host CSPRNG (`+random`); n below 0 is `E_RANGE`, above the value limit `E_LIMIT_VALUE`                                       |
  | `random:below`    | `( n:int -- int )`                 | uniform in [0, n) by rejection sampling, n of 1 or more (`E_RANGE` otherwise), big integers allowed                                                  |
  | `random:between`  | `( lo:int hi:int -- int )`         | uniform in [lo, hi], both ends included, `E_RANGE` when lo is above hi                                                                               |
  | `clock:now-ms`    | `( -- int )`                       | the Unix time in whole milliseconds (`+time`)                                                                                                        |
  | `clock:now-s`     | `( -- int )`                       | the Unix time in whole seconds, rounded down (`+time`)                                                                                               |
  | `list:sort`       | `( items:list -- list )`           | stable ascending sort of numbers (int and num together, big integers fine) or of strings (by code point); a mix, or any other element, is `E_COERCE` |
  | `list:sort-by`    | `( items:list keys:list -- list )` | the items in the stable ascending order of their keys (the same rules as `sort` apply to the keys); unequal lengths are `E_RANGE`                    |
  | `list:shuffle`    | `( items:list -- list )`           | a uniform random permutation (Fisher-Yates on the CSPRNG, `+random`)                                                                                 |
  | `list:unique`     | `( items:list -- list )`           | the strings of a list with repeats dropped, each at its first position (FL over a record, linear); another element type is an error                  |

  To sort by something other than the value, compute a key per item with `map` and use `sort-by` (inside a word with named inputs, the input is a local, so push it again: `items items [ lower ] map list:sort-by` is a case-insensitive sort; `[ len ] map` sorts by length; a key built from `str>int` pieces sorts by IP address or by natural order). Measured with the default limits: sorting or shuffling 65,536 short strings or integers costs two VM steps; measured on one machine, sorting 65,536 short strings took about 70 ms, 65,536 integers about 17 ms and shuffling 65,536 elements about 0.3 s (one CSPRNG call per swap), against the default limit of 30 s.

- **No other source of randomness or time.** Do not add a `_now` or `_random-*` primitive (none is left), and never read `Math.random`, `Date` or `crypto` from a new primitive. A word that calls a shared word carries the `+random` or `+time` effect (the compiler infers it).
- **How nondeterministic ops are tested.** An op with `+random` or `+time` cannot have a fixed output vector. Its `.test.json` holds the vectors that are deterministic (a range of size one, an empty count) and the error vectors (`E_RANGE`, `E_PARAM_INVALID`). `src/<vocab>.test.ts` checks the structure: length, alphabet, range, that two calls differ, a chi-squared check of the spread (a loose bound, such as 25 for 5 degrees of freedom, so the test does not flake), and exact values with the source pinned: stub `crypto.getRandomValues` with `vi.stubGlobal("crypto", { getRandomValues })` (see `src/prng.test.ts` and `src/list.test.ts`, which pin the rejection sampling and the Fisher-Yates swaps) and fake the clock with `vi.useFakeTimers({ toFake: ["Date"] })` and `vi.setSystemTime` (see `src/clock.test.ts`). `runtime.call` does not fill in header defaults, so pass every argument in a test.
- **Defaults, order and layout follow CyberChef.** The wave 5 close-out compared every op with CyberChef (see PLAN.md, "Wave 5 close-out"). Where the choice is arbitrary, a default, an order, a padding or a report layout, Forge does what CyberChef does, so a recipe moved from CyberChef gives the same result: Get Time counts seconds, the integer generator separates with a space, MOD takes a modulus and joins with a space, Extended GCD, Power Set, File Tree, To Table and Parse UNIX file permissions write CyberChef's layouts, Pad lines adds a number of characters, Wrap cuts at 64, units round to 20 decimal places, Expand alphabet range joins without a delimiter, Remove Diacritics leaves strokes alone, Unicode Text Format has both marks off, Diff compares characters, the TOTP account is Account with a 20-byte random secret, and so on. The differences that stay are deliberate and each is in the coverage note of its row: errors instead of silent ignoring, exact decimals, text instead of HTML, code point order instead of the host's locale, and the places where CyberChef's own result is wrong (a fathom, the Bezout identity for a negative number, the TOTP epoch). A vector for a changed behaviour comes from a standard or an independent computation (Python, RFCs), never from CyberChef's output.
- **Categories.** `category` is free text in the catalogue schema, and the UI groups by it; use these for wave 5 so the groups stay few: `Utils` (line and list ops, diff, tables), `Arithmetic`, `Date/Time`, `Extractors`, `Generators` (the random generators of `prng`, UUID, TOTP, Lorem Ipsum, De Bruijn), `Language` (diacritics, NATO, leet, Unicode text format, HTML to text), `Conversions` (units, co-ordinates), `Text` (the existing group, for string and byte ops), `Analysis` (the existing group). Do not invent others without telling the orchestrator.
- **The shared vocabularies are internal.** `random` and `list` are in `INTERNAL_VOCABS` because a public word with one input and no UI-typed parameter is a catalogue op by the rule of RECIPES.md section 2.2, and `random:below ( n -- int )` would have appeared in the UI. The ops built on them live in `prng`. `clock` is not internal: its shared words have no input, so they are not ops, and `clock:get-time` is the one op. (Any new shared word with no input needs no such care; one with inputs belongs in an internal vocabulary.)

## Wave 6 conventions

Wave 6 (compression and archives) puts codecs behind minimal private primitives and keeps the containers in FL. WP 5.39 built the `deflate` vocabulary as the exemplar (`vocab/deflate.fth`, `src/prims/deflate.ts`); the later WPs follow these rules.

Licences follow how `@noble/*` is attributed: a paragraph per library in the repository's `NOTICE` (fflate, lz-string, fzstd, brotli with base64-js, lzma1).
The Brotli decoder is vendored under `src/vendor/brotli` (no runtime dependency on the `brotli` package); each change is marked in its source and listed in NOTICE.

**Why `lzma1` and not `lzma` (lzma-js, which CyberChef uses).** `lzma` 2.3.2 has no ESM build and its code, `src/lzma_worker.js` (and the `lzma-c.js`, `lzma-d.js` variants), installs a global `onmessage` handler when it sees a worker scope (`typeof onmessage != "undefined"`), which would replace the bake worker's own message handler, and it ends with `this.LZMA = ...`, which throws where `this` is undefined (ES modules). That cannot be imported into the bake Worker safely. `lzma1` 0.6.1 (a maintained fork and port of XZ for Java's LZMA, `.lzma` compatible with `xz --format=lzma`, 7-Zip and the LZMA SDK) imports cleanly, is synchronous, offers levels 1 to 9 and does not touch globals. The version is the newest one published at least two weeks before 2026-11-11 (0.6.1, 2026-10-16; the package moves fast and 0.6.2 and later are younger). Consequence for 5.43: the decoders interoperate with lzma-js and `xz`, but the compressed **bytes** will differ from CyberChef's (a different encoder), so compression is tested by round trip and by an independent decoder (`xz --format=lzma -dc`), and decompression vectors come from `xz`/Python's `lzma` module. `lzma1.decompress` has no output cap: 5.43 must apply the bomb rule (read the declared size of the 13-byte header before decoding when it is known; use the streaming `Decompress` otherwise) and must not trust the header size to allocate.

### Category

`Compression` for every wave 6 op, archives included (CyberChef's own group). `Archives` is not a separate category.

### Bytes, errors and levels

- **Bytes in, bytes out.** Compress and decompress ops take and return `bytes`. The first parameter is the data and is named `data`.
- **Errors.** Corrupt or cut-short compressed data is `E_COERCE`, with a message that starts with the fault (`unexpected EOF`, `invalid block type`, `gzip checksum mismatch ...`, `gzip data is cut short`). Never leave a truncated stream undetected, and never return partial output for a stream that failed. A bad parameter (a level outside its range, a start index past the input, a name that cannot be stored) is `E_RANGE`, checked in the **word body** as earlier waves do (a header constraint would raise `E_PARAM_INVALID` or `E_RECIPE_INVALID`). The check is `_check-range ( n lo hi what -- )` in `deflate.fth`, carrying the marker `\ util-candidate: check-int-range`; copy it unchanged into your vocabulary with the marker, and the close-out promotes it. A primitive that is also called from TypeScript checks its own arguments too (`E_RANGE` through `rangeFailure`).
- **Checksums are verified by default** (`verify:bool=true` on the decoders of containers that carry one), and a failure is `E_COERCE`. CyberChef's decoders do not verify by default; turning `verify` off returns the data despite a bad trailer, which is how a damaged file is recovered. A decoder never reads a size from the data to decide how much to allocate.
- **Levels.** One parameter in every compressor: `level:int=<default>`, a plain `int` (no header constraint), checked in the word body (`E_RANGE` outside the format's range). The scale is the zlib one: **0 stores** (no compression), 1 is fastest, 9 is smallest; a format without a store mode starts at 1. The default is 6 where the library has one (CyberChef has no level for most of these ops). CyberChef's **Compression type** menu of Raw Deflate, Zlib Deflate and Gzip (Dynamic Huffman Coding, Fixed Huffman Coding, None) maps like this: None is level 0 (stored blocks, identical to zlib's for inputs up to 65,531 bytes; zlib cuts longer ones into other block sizes), Dynamic Huffman Coding is any level from 1 (fflate picks a stored, fixed or dynamic block for each block by size; the default 6 is the "dynamic" default), and **Fixed Huffman Coding is not offered** (no library gives a fixed-only encoder, and it has no use except to produce a particular byte string). The coverage note of each row says so.
- **Determinism.** A compressor gives the same bytes for the same input and parameters on every run: no op reads the clock or the random generator. A format's timestamp is a parameter that defaults to 0 (`gzip` has `mtime:int=0`, Unix seconds, where CyberChef writes the current time; ZIP's and tar's `mtime` do the same, 0 meaning the format's earliest time: ZIP 1980-01-01 00:00, tar the epoch). The OS byte of gzip is 255 (unknown).

### The output limit (decompression bombs)

A few kilobytes can expand to gigabytes. **Every decompressor stops at a maximum output size and raises `E_LIMIT_VALUE`** instead of allocating without bound. One rule:

1. **Which limit.** `limits.maxValueBytes` of the run (16 MiB for an untrusted bake, 64 MiB by default, from `UNTRUSTED_LIMITS` in `packages/worker/src/types.ts` and `DEFAULT_LIMITS` in `packages/lang/src/types.ts`). It is the largest single value the VM will accept anyway, so a decompressor that stopped there loses nothing a recipe could have used. There is no parameter for it.
2. **How a primitive learns it.** Every primitive receives the `PrimitiveContext` as its last argument; read `ctx.limits.maxValueBytes`. Test code calls the TypeScript function with an explicit limit, and calls through the runtime with `runtime.call(op, args, { limits: { maxValueBytes } })`.
3. **How it stops.** While decompressing, not afterwards. A streaming decoder pushes each chunk it emits into `new BoundedOutput(max)` (`src/prim-util.ts`); the chunk that would pass `max` raises `bombFailure(max, produced)`, which is `E_LIMIT_VALUE` with `detail.limit` `maxValueBytes` and the message `decompressed data of N exceeds the limit of M`. A library with no streaming interface and no cap is not used on untrusted data without checking a declared size first (and the declared size is checked, never trusted: it only rejects early).
4. **Feed the decoder in small input chunks**, so one step cannot expand past the cap by much: DEFLATE expands at most 1032 times, so `inflateLimited` pushes `max / 2064` input bytes at a time (at least 256), and the memory stays under about 1.5 times `max` plus 264 KiB. Measured: a 1 GiB bomb (1 MiB compressed) stops in 78 ms against 16 MiB and 136 ms against 64 MiB.
5. **Words that join pieces in FL** (concatenated gzip members) rely on the VM's own value limit for the joined result, in addition to each piece being capped.
6. **Tests.** Every decompressor has a bomb test (a stream that expands to far more than a small limit, `E_LIMIT_VALUE`), a test that exactly the limit passes and one byte more does not, and a test that a size field that lies (a gzip trailer claiming 4 GiB) allocates nothing.

### Checksums

Containers take their checksums from the shared words: `adler32:checksum` and `crc:checksum` with the preset `CRC-32`, which keep the parameters, the presets and the formatting in FL and run the per-byte loop in a private primitive each (`adler32:_adler`, `crc:_crc`). A checksum is therefore a few hundred VM steps for any length (the FL loops cost 13 VM steps a byte and capped an input near 750,000 bytes under the default limits and 380,000 bytes for an untrusted recipe). Measured at the close-out (WP 5.46a), 16 MiB: `deflate:gunzip` 365 steps and `deflate:zlib-inflate` 173 steps, `crc:checksum` CRC-32 130 steps; all under both the default and the untrusted limits (`src/large-inputs.test.ts`). A new container uses these words; it does not write its own checksum loop.

### Archives (Zip, Unzip, Tar, Untar: WP 5.40)

The `file` value type is not implemented (PLAN 3.1) and an output is one `OutputValue`. What the output pane can show was checked in `apps/web/src/io/forge-output.ts` and `packages/worker/src/render.ts`: a `list` or a `record` renders as an expandable tree (`renderTree`), up to 1,000 items per list and 6 levels, with a `bytes` leaf shown as its text (cut at 200 characters) or as the length and the first 16 bytes in hex; copy and download give the same structure as text (`describeValue`). Existing ops already return lists (`regex:find-all`, `analysis:frequency`, the brute-force ops), and the vector format can expect a list or record with `{ "json": ... }`, a `bytes` value written `{ "$bytes": "<hex>" }`. The data-driven smoke test of `apps/web/e2e/ops-smoke.spec.ts` only picks vectors that expect text or bytes, so a vector that expects `json` is skipped there (not failed); the vector run of `gate4:browser` covers it.

The rule of wave 5, "do not return an FL `list` from an op", was about line and list _utilities_: a list output has no way into the next step (the next op's data input is `bytes`, and a `list` has no coercion to it: `E_TYPE`), so a text transform must give `str` and take a delimiter. An archive listing is a **terminal inspection result**, not a value to chain, so it may be a `list`; the rule stays for everything that is meant to be chained. Decisions:

- **Unzip and Untar** return a `list` of `record`s, one per entry in archive order, with these keys in this order and always present: `name:str` (the path as stored), `size:int` (bytes of `data`), `dir:bool`, `mtime:int` (Unix seconds; ZIP's DOS time is read as UTC; 0 when the format has none), `mode:int` (the Unix permission bits, e.g. 420 for 0o644; 0 when the format has none) and `data:bytes` (empty for a directory). Further keys only where a format has them and CyberChef shows them (say so in the coverage note).
- **Taking one entry to continue a recipe**: a separate op for each format that returns `bytes`, `unzip:entry ( data:bytes name:str password... -- bytes )` and `untar:entry ( data:bytes name:str -- bytes )` (WP 5.40 chooses the final names; they are not CyberChef rows, and the coverage notes of Unzip and Untar mention them). An entry that is not there is `E_RANGE` and the message lists the first entry names. These are also the ops the UI smoke test and the browser gate exercise with bytes expectations.
- **Zip and Tar** take the input as one file with a `filename:str` parameter (CyberChef's way) and return `bytes`; the format fields (comment, mode, mtime, uid, gid) are parameters with deterministic defaults. A recipe cannot yet build an archive of several files; that waits for the `file` type.
- **Bombs in archives**: each entry is capped by the output limit as above, **and** the sum of all entries (a zip of a thousand 16 MiB entries would otherwise reach 16 GiB): the listing stops with `E_LIMIT_VALUE` when the total passes `maxValueBytes`. Declared sizes only reject early.
- If a later look shows that the list-of-records result does not suit the pane, the alternative is text: one line per entry (`name  size  mtime`) as `str`, plus the entry op above. Do not implement that unless asked.

### Cross-check with CyberChef (wave 6 close-out, WP 5.46b)

Every wave 6 CyberChef row was compared with CyberChef 11.5.0's own operation modules (see PLAN.md, "Wave 6 close-out"): the streams of each side decode on the other, defaults and option names already followed CyberChef, and the differences that stay are in the coverage notes. It found one Forge bug (stored DEFLATE blocks at multiples of 65,535 bytes, fixed in `deflate:_deflate`) and several CyberChef defects that Forge does not reproduce (the Fixed and None types on an empty input, LZMA text as Latin-1, the LZNT1 one-byte chunk, XPRESS Huffman with one block and a different bit-buffer refill). A new compressor is checked with the library's own independent decoder before it is merged, and a decoder with the test encoder's streams.

### Vectors

- **Decompressor vectors come from independent tools**: Python's `zlib`, `gzip`, `bz2`, `lzma` modules, the command line tools (`gzip`, `xz`, `bzip2`, `zstd`, `brotli`, `tar`, `zip`, `unzip`) and RFC examples. `ref` names the tool and call, and the vector file is generated by a script kept out of the repository; a value that could not be computed independently is flagged in the WP report, never invented.
- **Compressor outputs depend on the library.** Test them by round trip, by "an independent tool decompresses the output" (in a test with Node's `zlib` where it has the format, `node:zlib` is declared in `src/ambient.d.ts`; otherwise during development, recorded in the report), and pin exact compressed bytes only where the output is deterministic for the pinned library version (the stored mode of DEFLATE is fixed by RFC 1951 and equals zlib's byte for byte up to 65,531 bytes, where zlib starts to cut the blocks differently; other levels are pinned to the fflate 0.8.3 output and checked by decompression). Never use CyberChef's output as a vector.
- **Also required**: the empty input, a 64 KiB round trip with a Vitest timeout of 60,000 ms and the measured step count, corrupt input, truncated input at several cut points, the bomb tests above, and each `E_RANGE` case.

## Wave 7 conventions

Wave 7 (public key, networking, forensics, binary and text data formats, and the stragglers of earlier waves) parses and builds structured binary data. WP 5.47 built the shared ASN.1 layer and the `asn1-dump`, `oid` and `pem` ops as the exemplar; the later WPs (5.48 to 5.59, PLAN.md "Wave 7") follow these rules.

### Libraries

`@noble/curves` 2.4.0 is pinned to an exact version (MIT, Copyright Paul Miller, attributed in `NOTICE`). It was published on 2026-08-27, more than two weeks before 2026-11-11, and its only dependency is `@noble/hashes` 2.4.0, the version already pinned. WP 5.47 added it and a smoke test (`src/noble-curves.test.ts`); WP 5.51 (ECDSA, SM2, GOST R 34.10) is its user; WP 5.50 (RSA) uses no library (below). The rules:

- **Import from the subpath modules, with the `.js` suffix, only inside the primitive file of the vocabulary** (`src/prims/<v>.ts`): `@noble/curves/nist.js` (`p256`, `p384`, `p521`), `@noble/curves/secp256k1.js`, `@noble/curves/abstract/weierstrass.js` (`weierstrass` and `ecdsa`, for a curve given by its parameters: SM2 and the GOST curves), `@noble/curves/abstract/modular.js` for field helpers. Never the package root. The vocabulary's lazy chunk then holds only the curves it uses.
- **The library never reads the host's random generator.** It would, by default (`randomSecretKey()`, and `randomBytes` inside a custom curve). A key generator takes its bytes from `random:bytes-of` in FL and passes them in (`randomSecretKey(seed)`, or the bytes as the private key after the range check), so the op carries `+random` and tests can pin the source (see "Wave 5 conventions"). A signature is deterministic (RFC 6979, `extraEntropy: false`, the default) unless the op documents otherwise.
- **State the options every call depends on.** In noble 2.x `sign` and `verify` hash the message with SHA-256 first (`prehash: true`) and refuse a signature with a high `s` (`lowS: true`). OpenSSL and CyberChef do neither, so an op passes `prehash: false` after hashing in FL (the hash is a parameter, as in CyberChef) and `lowS: false` for verification, and documents the choice. Signatures are DER or raw `r||s` as the op's parameter says; the DER form is written with the `asn1` words, not with the library.
- Test against independent tools: `openssl pkeyutl`, `openssl dgst -sign`, `openssl ecparam` and Python's `cryptography` (a key generated and a signature made there verify here, and the reverse), plus the RFC 6979, SM2 (GB/T 32918) and GOST R 34.10 published vectors.

RSA (WP 5.50) has no library: the arithmetic is on bigints in a small private primitive (modular exponentiation is core `powmod`; the primitive is for key generation's prime search and the CRT only if FL is too slow), with PKCS#1 v1.5, OAEP and PSS padding in FL over the hash vocabularies and the `asn1` words.

### Category

Use CyberChef's own category names so the UI groups stay few: `Public Key` (ASN.1, OIDs, PEM, X.509, CSR, CRL, RSA, EC, SSH keys, JWK), `Networking` (packets, addresses, URIs, user agents, fingerprints), `Data format` (CBOR, MessagePack, Protobuf, CSV, JSON, YAML, TLV, QR), `Forensics` (file type, embedded files, EXIF, ID3, ELF, YARA), `Extractors` and `Other` for the stragglers of earlier waves (the existing groups, with the existing names). Do not invent others without telling the orchestrator.

### How a parser reports

1. **An op that shows what is inside a structure returns `str`**: an outline or a report that is read and copied, in CyberChef's layout where the author knows it (two spaces of indent per level; `Name: value` lines; a blank line between records). Parse ASN.1 hex string is the exemplar: `asn1-dump:parse` is text, in the shape of the jsrsasign dump CyberChef prints. Reasons: the output pane shows a `list` or `record` tree only 6 levels deep and 1,000 items wide (`renderTree`), a certificate nests deeper once its extension values are opened; text copies, downloads and searches; and CyberChef's ops give text. A value that is data (a key, a signature, a payload) also has an op that returns it as `bytes` or hex, so a recipe can continue (CyberChef has them too: Public Key from Certificate, Hex to PEM).
2. **`list` of `record`s only for an archive-like result whose items carry binary payloads** that a text report would have to hex-dump (Unzip and Untar, wave 6 conventions), with a bytes-returning entry op. Do not return a `list` to be chained (wave 5 rule).
3. **The shared parsers return records and lists to FL code, not text.** They live in an internal vocabulary (below) and the op turns them into text. A new binary format that two or more ops need gets such a vocabulary, with a node record documented in its header comment.
4. Hex in the name means hex text: **CyberChef's "Hex to X" and "X to Hex" ops take and give hex text** (`str`, digits read as in From Hex, white space ignored, written in lower case with no separator). Do not add a `bytes` variant; a recipe that has bytes uses To Hex or From Hex next to the op.
5. Trailing bytes after the structure are `E_COERCE` unless the format defines them (`asn1:parse` wants exactly one element; `asn1-dump:parse` shows every element from `start` and refuses bytes that are not an element).

### Errors and bounds

- **Malformed or hostile data is `E_COERCE`**, with a message that starts with the fault and gives the offset (`the element at offset 12 declares 300 bytes but only 4 are left (truncated)`). A cut-short input is never accepted as shorter data and never returns partial output. A bad parameter (an index past the input, a label that cannot be written, a count out of range) is `E_RANGE`, checked in the **word body** (`util:check-int-range`; a header constraint would raise `E_PARAM_INVALID` or `E_RECIPE_INVALID`). A result that would pass the value limit is `E_LIMIT_VALUE`.
- **Nothing is allocated from a number in the data.** A length, a count or an offset is only compared with the bytes that exist. A recursive structure has a depth limit (64 for ASN.1: `asn1:max-depth`), checked before the descent; the reader is iterative or recursive to that depth only. The number of items is bounded by the input (an ASN.1 element is two bytes at least), and a primitive that builds a record tree stops with `E_LIMIT_VALUE` once the estimated size passes `limits.maxValueBytes` (about 320 bytes of value budget per node, so under the 16 MiB of an untrusted bake about 52,000 nodes; the 64 MiB default allows about 200,000).
- **Measure at 64 KiB** and record the VM steps in the test, as in earlier waves. Measured for the ASN.1 layer (61 KB, 4,000 elements): `asn1:parse-all` 11 steps and 8 ms; the outline `asn1-dump:parse` 983,000 steps (about 245 per element: 40,000 elements fit the 10 million step default); `pem:from-hex` 17,900 steps; `pem:to-hex` 55 steps.
- A primitive checks its own arguments too (`rangeFailure`), as it can be called from TypeScript.

### The shared vocabularies are internal

Words that other vocabularies call, and that take or return a type the UI cannot edit (a record, a list of nodes), live in an **internal vocabulary** in `INTERNAL_VOCABS` (`packages/ops/src/types.ts`; add the name and the list in `src/catalogue.test.ts`). Ops live in public vocabularies named after the CyberChef feature. Two gotchas found in WP 5.47:

- `see-also` is a load dependency, so two vocabularies cannot see-also each other (`vocabulary dependency cycle`); the ops of one family point one way.
- A `try` quotation cannot reach values under its snapshot (they are below its floor, `E_STACK_UNDERFLOW`): read the data in the body from locals, and have the handler leave the stack as the body would.

### The `asn1` vocabulary (WP 5.47)

`asn1` is internal: DER reading and writing, object identifiers and PEM, for X.509, CSR, CRL, SSH keys, RSA, ECDSA and JWK. Call the words qualified (`asn1:parse`) or with `USING: asn1`. The reader is one primitive (`parse-in`), measured against FL (a few hundred VM steps per element and quadratic list growth); everything else is FL over it, or a table lookup in a primitive because FL has no per-vocabulary constants (a record of 250 OID names rebuilt per call costs thousands of VM steps; a primitive builds its maps once and a lookup is 2 steps).

**The node record** (`parse-in`, `parse-all`, `parse`): `class` (`universal`, `application`, `context` or `private`), `constructed` (bool), `tag` (int), `offset` and `hlen` (where the element starts and how long its identifier and length octets are, in the data it was read from; offsets are always into the original data, also for a window), `len` (content bytes), `value` (the content of a primitive element, a copy; **empty for a constructed one**, whose content is `children` or `asn1:content`) and `children` (list of nodes, empty for a primitive element). Reading is BER-tolerant for definite lengths (a non-minimal length or tag is accepted so other tools' output can be inspected); an indefinite length, an end-of-contents marker, a reserved length byte, a header cut short, a child that runs past its parent, and nesting deeper than the limit are `E_COERCE`. The writers always produce DER.

### Vectors and the cross-check

- **Vectors come from independent tools**: `openssl` (`asn1parse -genstr`, `x509`, `req`, `pkey`, `ecparam`, `enc -base64`), Python's `cryptography`, `hashlib`, `struct`, the standards' own examples (X.690 annexes, RFC 4648, 5280, 7468, 8032, 8017), `tshark`/`scapy`-style packet captures written by hand from the RFC. `ref` names the tool and call; the vector file is generated by a script kept out of the repository. **Never use CyberChef's output as a vector**, and flag any expected value that could not be computed independently.
- **A text report's layout is Forge's choice**, so its expected text may be written by the author, but every value in it (names, numbers, strings) must be compared with an independent tool, and the vector's `ref` says so.
- Also required for each op: the empty input, a truncated input at every cut point (a test loop, as `asn1.test.ts` does for a certificate), deep nesting at the limit and one over, long-form lengths, lying lengths that allocate nothing, mutated input that must give `E_COERCE` or a result and nothing else, and each `E_RANGE` case.
- **Cross-check expectations.** The wave 7 close-out (WP 5.59) compares every op with CyberChef 11.5.0's own operation modules, as in waves 5 and 6. Until then, follow CyberChef's defaults, parameter order and layouts where the author knows them and say in the coverage note which are from memory and not verified. A difference that stays (an error instead of silent ignoring, a stricter parser, text instead of HTML) goes in the coverage note of the row.

### RSA (WP 5.50)

`rsa` holds the six RSA operations of CyberChef's Public Key category, with no library: the arithmetic is the core `powmod`, `invmod` and `gcd` on bigints, the padding is FL over the digest words (`md5`, `sha1`, `sha2`) and MGF1, the keys are read and written with the `asn1` words, and the only primitive is the prime search of key generation (above). The `rsa` words are all ops (`rsa` is a public vocabulary: the key readers and writers are private `_` words, so WP 5.49 and 5.51 write their own or promote them at the close-out).

| Op                      | Stack effect                                                                                                                                                                                       | Meaning                                                                                                                       |
| ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `rsa:generate-key-pair` | `( bytes size:choice{1024\|2048\|4096}="2048" format:choice{PEM\|JWK}="PEM" -- str )`                                                                                                              | the public key (`PUBLIC KEY`, SPKI) then the private key (`RSA PRIVATE KEY`, PKCS#1) as PEM, or one JSON line each; `+random` |
| `rsa:sign`              | `( data:bytes key:str password:str="" digest:choice{SHA-1\|MD5\|SHA-256\|SHA-384\|SHA-512}="SHA-1" scheme:choice{RSASSA-PKCS1-V1_5\|RSASSA-PSS}="RSASSA-PKCS1-V1_5" salt-length:int=-1 -- bytes )` | the signature; `+random` (PSS draws the salt)                                                                                 |
| `rsa:verify`            | `( data:bytes key:str message:key{utf8\|hex\|latin1\|base64}="" digest scheme salt-length:int=-1 -- str )`                                                                                         | the input is the signature; `Verified OK` or `Verification failure`                                                           |
| `rsa:encrypt`           | `( data:bytes key:str scheme:choice{RSA-OAEP\|RSAES-PKCS1-V1_5\|RAW}="RSA-OAEP" digest="SHA-1" -- bytes )`                                                                                         | `+random`                                                                                                                     |
| `rsa:decrypt`           | `( data:bytes key:str password:str="" scheme digest -- bytes )`                                                                                                                                    | one error for every failure                                                                                                   |
| `rsa:public-key`        | `( key:str format:choice{PEM\|DER\|JWK}="PEM" password:str="" -- bytes )`                                                                                                                          | the SPKI public key of a private key (RSA only so far)                                                                        |

All six are in the category `Public Key`.

**Keys.** The key parameter is PEM text. Public keys are `PUBLIC KEY` (SubjectPublicKeyInfo) or `RSA PUBLIC KEY` (PKCS#1); private keys are `RSA PRIVATE KEY` (PKCS#1), `PRIVATE KEY` (PKCS#8) or encrypted. The first block of an accepted label is used, so the text Generate RSA Key Pair writes (public block, then private block) can be pasted into any of the ops, and so can text with comments around the blocks. The structure, not the label, tells SPKI from PKCS#1 and PKCS#8 from PKCS#1. A key record in FL is `{ n e }` or `{ n e d p q dp dq qi }`. Encrypted private keys (CyberChef's "Key Password" of RSA Sign and RSA Decrypt, added here to Public Key from Private Key too): the legacy `Proc-Type: 4,ENCRYPTED` / `DEK-Info` PEM with AES-128/192/256-CBC, DES-EDE3-CBC or DES-CBC (OpenSSL's MD5 EVP_BytesToKey over the password and the first 8 bytes of the IV), and PKCS#8 `ENCRYPTED PRIVATE KEY` with PBES2 (PBKDF2 with HMAC-SHA-1, -256, -384 or -512, and AES-128/192/256-CBC, DES-EDE3-CBC or DES-CBC), through the `evp`, `pbkdf2`, `aes`, `triple-des` and `des` words. Other schemes (PBES1, scrypt, HMAC-SHA-224 and -512/xxx PRFs) are `E_RANGE`. A key that is encrypted and given no password is `E_RANGE` ("give its password"); a wrong password is `E_COERCE` ("the password is wrong or the key is damaged": a decryption with the wrong password ends in a padding error or in bytes that are not DER, which cannot be told from damage).

**Errors.** A text with no usable block, a key of another algorithm (an EC key, with the hint that EC keys are not supported yet), multi-prime RSA, a missing password and a message or parameter that does not fit the key are `E_RANGE`. A damaged key (bad DER, p times q not n, a private operation that the public one does not invert, which also catches a fault in the CRT) is `E_COERCE`. Verification never raises for a bad signature: any fault (length, value, padding, digest, salt) is `Verification failure`. **Decryption raises one error for every fault**: `E_COERCE` with the message `cannot convert str to bytes: decryption error`, whether the ciphertext has the wrong length or is not below the modulus, the leading byte, the hash, the separator or the padding is wrong, or the digest is not the one used (`src/rsa.test.ts` builds OAEP and v1.5 blocks with each fault and compares the messages). JavaScript cannot make the work constant-time, so a timing difference between the faults remains; the message is the only thing the op reports.

**Schemes** (RFC 8017). RSAES-OAEP: empty label, MGF1 with the OAEP digest (OpenSSL's and node-forge's default), `hLen` random seed bytes from `random:bytes-of`. RSAES-PKCS1-v1_5: padding of nonzero random bytes (zero bytes are dropped and redrawn). RAW: the message as a big-endian number below the modulus, the result `k` bytes (decryption keeps the leading zeros). RSASSA-PKCS1-v1_5: the DigestInfo is built with the `asn1` words and the digest OIDs of RFC 8017 (MD5, SHA-1, SHA-256/384/512), verification re-encodes and compares. RSASSA-PSS: MGF1 with the same digest, salt `salt-length` bytes (-1: the digest length for signing, any length for verifying), `emBits = modBits - 1` for any modulus size. The private operation is CRT over `powmod`, checked by the public exponent; a key without its prime factors (p or q 0) uses `d` directly.

**Key generation.** Public exponent 65537; two primes of `size/2` bits with the top two bits set (so the modulus has exactly `size` bits), `p - 1` and `q - 1` prime to the exponent, `|p - q|` above `2^(size/2 - 100)`, `d = e^-1 mod lcm(p - 1, q - 1)`, `p > q`. The primes come from `_prime`: candidates cut from pools of 32 KiB of `random:bytes-of`, trial division by the primes below 65536, a Fermat test to base 2, then 13 Miller-Rabin rounds (base 2 and 12 random 128-bit bases: the error bound 4^-13 holds for any candidate and is far below the 2^-100 of FIPS 186-5 B.1 for random candidates of 512 bits and up). The search gives up with `E_USER` after 200 pools (a broken random source; it never happens with a real one, and a source that returns only zeros ends this way). Tests pin the source by stubbing `crypto.getRandomValues` (`src/rsa.test.ts`: the same stream always gives the same key; the 1024-bit result is checked with `openssl rsa -check`).

**Measured** (Node 22, one core; each is a single op call): `powmod` 27 ms for 2048 bits, so the CRT private operation of a 4096-bit key is two of them, 55 ms. Sign (PKCS#1 v1.5 or PSS), 1024-bit key: 5,430 VM steps, 7 ms; 2048-bit: 9,404 steps, 13 ms; 4096-bit: 17,340 steps, 61 ms; a 64 KiB message adds nothing but the digest (2048-bit key, SHA-256: 9,404 steps, 18 ms). OAEP decrypt, 2048-bit: 13,150 steps, 61 ms; 4096-bit: 25,723 steps, 69 ms. Encrypt, 4096-bit: 7,288 steps, 14 ms. Verify, 4096-bit: 15,035 steps, 10 ms. About 4 steps per modulus byte come from `util:zero-bytes` and `count-leading`. Key generation (real random source): 1024 bits 35 ms on average, 2048 bits 240 ms, 4096 bits 1.8 s (median 1.4 s, slowest of twelve runs 3.4 s); 3,000 to 4,200 VM steps. The limit on the time is therefore not reached; there is no cap on the work beyond the 200 pools.

**Differences from CyberChef** (from memory of its source; WP 5.59 compares them): hash list and order are CyberChef's (SHA-1 first); RSA Sign and RSA Verify are PKCS#1 v1.5 only in CyberChef, PSS is an addition behind the `scheme` parameter (default unchanged); Verify takes the message as a parameter and the signature as the input, with the result texts `Verified OK` and `Verification failure`; Generate RSA Key Pair writes LF where node-forge writes CRLF, has no DER output format, and its JWK output is an assumption (public key, private key, one line each); Public Key from Private Key reads RSA only (an EC key is `E_RANGE`: **WP 5.51 extends it** in `vocab/rsa.fth`: `public-key` calls `_private-key`, which refuses an EC key in `_find-block` (the label `EC PRIVATE KEY` is not in its list) and in `_check-oid` (the PKCS#8 algorithm OID `1.2.840.10045.2.1`); 5.51 should read the first private block itself in `public-key`, and when its label is `EC PRIVATE KEY` or its PKCS#8 algorithm is that OID, hand the DER and the format to a word of its own `ecdsa` vocabulary and return that. `rsa` then uses `ecdsa`, so `ecdsa` must not use `rsa`: a `USING` or `see-also` cycle is refused) and adds the password parameter; keys must be PEM (no DER or hex keys, no certificates); decryption failures are errors where CyberChef returns forge's error text; RAW decryption keeps leading zeros.

**Vectors** (`vocab/rsa.test.json`, 104): signatures from `openssl dgst -<digest> -sign` for the five digests and for 512-, 1024-, 2048- and 4096-bit keys (deterministic, so exact), keys in PKCS#1, PKCS#8, legacy encrypted (`openssl rsa -traditional -aes128|-aes192|-aes256|-des3|-des`) and PBES2 (`openssl pkcs8 -topk8 -v2 aes-256-cbc|aes-128-cbc|aes-192-cbc|des3|des-cbc` with the PRFs hmacWithSHA1, -256, -384, -512); PSS signatures from `openssl dgst -sigopt rsa_padding_mode:pss` for five digest and salt combinations; OAEP, v1.5 and raw ciphertexts from `openssl pkeyutl -encrypt`; public keys from `openssl rsa -pubout` and the JWK from Python `cryptography`; error vectors. `src/rsa.test.ts` adds the random parts with the source pinned, computed by a second implementation of RFC 8017 in Python (hashlib and `pow` only) and each opened or verified by openssl, and round trips with `node:crypto` (OpenSSL) in both directions. **Not available**: the RSA Labs `pkcs-1v2-1-vec` files (OAEP and PSS vectors) could not be reproduced exactly from memory, so no value from them is used; RFC 8017 has no test vectors of its own.

### Elliptic curves (WP 5.51: `ecdsa`, `sm2`, `gost3410`, `gost-mac`)

Category `Public Key` (`gost-mac` is `Encryption`, where CyberChef puts GOST Sign). The curve arithmetic is a private primitive per vocabulary over `@noble/curves` (rules in "Libraries" above); every other step is FL.

| Word                                    | Stack effect                                                                                                                                                                                           | CyberChef row                                                      |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------ |
| `ecdsa:generate-key-pair`               | `( data:bytes curve:choice{P-256\|P-384\|P-521}="P-256" format:choice{PEM\|DER\|JWK}="PEM" -- str )` (`+random`)                                                                                       | Generate ECDSA Key Pair                                            |
| `ecdsa:sign`                            | `( data:bytes private-key:str digest:choice{sha256\|sha384\|sha512\|sha1\|md5}="sha256" format:choice{asn1-hex\|p1363-hex\|jws\|raw-json}="asn1-hex" -- str )`                                         | ECDSA Sign                                                         |
| `ecdsa:verify`                          | `( signature:str input-format:choice{auto\|asn1-hex\|p1363-hex\|jws\|raw-json}="auto" digest public-key:str message:toggle{utf8\|hex\|base64\|latin1} -- str )`                                        | ECDSA Verify                                                       |

- **"GOST Sign" and "GOST Verify" are not signatures.** CyberChef's two ops (its `Ciphers` module) are the MAC modes of GOST 28147-89, Magma and Kuznyechik (key, IV, input/output type, algorithm, S-box, MAC length); the plan and the WP brief took them for GOST R 34.10. `gost-mac` is what the rows are: the GOST 28147-89 IMIT with CyberChef's parameters (Magma and Kuznyechik are not offered, as in `gost28147`, and nor are the Signal-COM S-boxes). The GOST R 34.10-2012 signature the brief asked for is `gost3410`, an addition with no CyberChef row. Its curves are the RFC 7091 test curves, the CryptoPro 256-bit sets A, B and C and the 512-bit set A; the signature is `r || s` as hex, k is random (`random:bytes-of`, with the standard's retry), and the Streebog digest (little-endian bytes of the number RFC 6986 prints) is read as the number alpha of RFC 7091. The RFC 7091 section 7 examples are reproduced at the level of the digest number `e`, so the byte order of the hash is a documented choice that no vector checks (OpenSSL's gost-engine, which could, is not in the sandbox).
- **ECDSA.** Keys are PEM: SEC1 `EC PRIVATE KEY`, PKCS #8 `PRIVATE KEY` and `PUBLIC KEY` are read (an `EC PARAMETERS` block in front is skipped; encrypted keys, explicit curve parameters and curves other than P-256, P-384, P-521 and secp256k1 are `E_COERCE`); new keys are written as CyberChef writes them, the public key first and then the PKCS #8 key (byte for byte what OpenSSL writes). The message is hashed in FL (`md5`, `sha1`, `sha2`) and the digest is passed to the primitive with `prehash: false`, `lowS: false`, `format: "compact"`, `extraEntropy: false`. **Signatures are deterministic (RFC 6979, HMAC of the same hash as the message)**; CyberChef (jsrsasign) picks a random k, so its signatures differ on every call. Verification accepts any valid signature, of either half of s. `ecdsa:sign` is pure; `generate-key-pair` takes `random:bytes-of` of the seed length of FIPS 186-5 appendix A.2 (the private scalar is `seed mod (n - 1) + 1`). Differences from CyberChef: secp256k1 keys are read as well; the digest is a choice named `sha256` and so on; the output formats are the choice `asn1-hex`, `p1363-hex`, `jws` and `raw-json`; verify answers `Verified OK` / `Verification Failure`, CyberChef's two texts; the `DER` output of the key generator is CyberChef's name for the raw private scalar in hex, which is kept; ECDSA Signature Conversion writes P1363 and JWS at the smallest of 32, 48 and 66 bytes that holds r and s (from memory of jsrsasign's `asn1SigToConcatSig`, which pads to multiples of 16 bytes and so cannot write a P-521 value; not run); `raw-json` writes the hex of the DER INTEGER content, as jsrsasign does, and reads r and s as unsigned hex with or without a leading `00`. The library is built from the SEC 2 parameters in `src/prims/ecdsa.ts` (checked against `nist.js` and `secp256k1.js` in the test), not imported from `nist.js`, which builds its curves with the host's generator and carries the hash-to-curve, FROST and OPRF code; every curve is created with a `randomBytes` that throws, which the library answers by not blinding, so no code path reads `crypto.getRandomValues` (tested).
- **SM2.** The curve `sm2p256v1` of GB/T 32918.5 (parameters checked against `openssl ecparam -name SM2 -param_enc explicit`); the KDF and C3 use the `sm3` words; k is `random:between 1 (n - 1)` (with the standard's retry if the key stream is all zero). As CyberChef writes it, C1 is `x || y` without the `04` byte and the ciphertext is hex; **decryption also accepts the `04` byte**, chosen by checking whether the 65 bytes are a point on the curve (a C1 whose x starts with `04`, like the one in the GB/T 32918.5 annex example, is therefore read correctly). The layout (hex text, C1 as `x || y`, the parameter names and orders) is from CyberChef 11.5.0's source, read for the layout only (no output was used); the wave close-out cross-check should run it.
- **Vectors.** ECDSA: RFC 6979 appendix A.2.5 to A.2.7 (also in `src/prims/ecdsa.test.ts`), deterministic signatures agreed by two independent implementations (Python `cryptography` over OpenSSL with `deterministic_signing=True`, and the `ecdsa` package), signatures made by `openssl dgst -sign` on all four curves, keys and public keys from `openssl ecparam`, `pkcs8` and `pkey`, and the generated PEM compared with the one Python `cryptography` writes. SM2: the encryption example of GB/T 32918.5-2017 annex A (message `encryption standard`; d, k, C1, C3 and C2 as published, reproduced by an independent Python implementation of GB/T 32918.4 and by `sm2:t-encrypt` with that k), and ciphertexts made by `openssl pkeyutl -encrypt` (SM2 key from `openssl genpkey -algorithm SM2`, its DER regrouped as C1C3C2 or C1C2C3) and ciphertexts of the Python implementation that `openssl pkeyutl -decrypt` accepts. GOST R 34.10: RFC 7091 sections 7.1 and 7.2 (public key, r and s from d, e and k), and an independent Python implementation for the other curves. `gost-mac`: a Python IMIT written from RFC 5830 that reproduces the CEK_MAC of the RFC 4357 key wrap references of `gost28147.test.json`, and the equality with `gost28147:wrap-key` for all eight S-boxes. The ops with a random output (`generate-key-pair`, `sm2:encrypt`, `gost3410:sign`) have only error vectors in the vector file; their output is tested with pinned seeds, k or a stubbed generator in `src/ecdsa.test.ts`, `src/sm2.test.ts` and `src/gost3410.test.ts`.
- **Cost** (VM steps; a 64 KiB message). `ecdsa:sign` 5,000 to 7,600 (P-256 to P-521) and `verify` 13,800 to 24,600, about 100 ms; `generate-key-pair` about 2,200; `convert-signature` of a 64 KiB hex text refuses or converts it in under 2 million steps, bounded by the integer size limit; `sm2:encrypt` and `decrypt` 412,000 steps (the KDF is 2,048 SM3 calls in FL: 200 steps a block), 0.2 to 0.35 s; `gost3410:sign` and `verify` under 5,000 (the Streebog hash is one primitive call); `gost-mac:sign` about 300 steps (one primitive call).

## JSON values (WP 5.48)

The `json` vocabulary is the one place where JSON text and FL values meet. Later work packages that read or write structured data (CBOR, MessagePack, YAML, Avro, JWK, JPath, Protobuf, X.509 reports, JWT claims, ...) turn their data into FL values and call these words, instead of building JSON text by hand or writing their own parser. `json` is internal (it is in `INTERNAL_VOCABS`, like `list` and `random`), so none of its words is a catalogue op; call them qualified or with `USING: json`. `parse`, `stringify`, `null` and `null?` are primitives (`src/prims/json.ts`); `compact` and `pretty` are FL.

| Word             | Stack effect                      | Meaning                                                                                                                                                                                                 |
| ---------------- | --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `json:parse`     | `( text:str -- any )`             | strict RFC 8259 text to a value: object to `record`, array to `list`, string to `str`, integer to `int`, other number to `num`, `true`/`false` to `bool`, `null` to `json:null`; bad text is `E_COERCE` |
| `json:stringify` | `( value:any indent:int -- str )` | a value to JSON text: compact for an indent of 0, else that many spaces per level (0 to 32, `E_RANGE` otherwise)                                                                                        |
| `json:compact`   | `( value:any -- str )`            | `stringify` with indent 0: `{"a":[1,2]}`                                                                                                                                                                |
| `json:pretty`    | `( value:any -- str )`            | `stringify` with indent 2                                                                                                                                                                               |
| `json:null`      | `( -- record )`                   | the value that stands for JSON null                                                                                                                                                                     |
| `json:null?`     | `( any -- bool )`                 | true if the value is `json:null`; works on every value                                                                                                                                                  |

### The rules

- **Null.** FL has no null, so JSON `null` is a dedicated sentinel: the `record` with the one key U+DFFF followed by `null`, whose value is `true`. It is a record so that it travels everywhere a value can (lists, records, equality: two nulls are `=`), and its key is a lone low surrogate, which `parse` refuses in every string and key (no UTF-8 text can hold one), so no JSON text can produce a record that is mistaken for null, and `stringify` refuses a lone surrogate, so the sentinel's key can never be written as an ordinary key. FL source can only make such a string by accident (a raw lone surrogate in the source text). `stringify` writes the sentinel as `null`, so null round trips (`[null,{"a":null}]` stays as it is). **`type` of a null is `"record"`**: always test `json:null?` before looking at `type` or reading a record. To put a null into a result, call `json:null` (a record is built with `>record` from `{ key value }` pairs, a list with `append` or a `map`). Printing a null in the console or in `.s` shows `record{ "\uFFFDnull": true }` (the lone surrogate is encoded as U+FFFD on output); in an op that returns JSON text it is `null`. Do not use an empty record, `false`, `0` or `""` for a missing value that JSON must show as `null`.
- **Numbers.** The text decides, not the value: a number written with only an optional minus and digits (no `.`, no exponent) is an exact `int`, a big integer if it needs one (`123456789012345678901234567890`; `-0` is the int 0); a number with a fraction or an exponent (`1.0`, `1e2`, `-0.0`) is a `num`. A `num` out of the range of a double (`1e999`) is `E_COERCE`; an `int` over `maxIntBits` is `E_LIMIT_VALUE` (checked before it is converted). `stringify` writes an `int` as exact decimal digits and a `num` with the shortest text that reads back as the same double, always with a fraction or an exponent (`100.0`, `-0.0`, `0.30000000000000004`, `1e+21`, `1e-7`), so `int` and `num` survive a round trip and a big integer never passes through `num`. (Python writes `1e-07`; the number is the same.) Do not turn a `num` that must be written as an integer into an `int` by hand; use `floor` or `num>int` first. NaN and the infinities cannot exist (`num` is always finite).
- **Strings.** Text is `str`; the escapes of RFC 8259 are read, and a pair of `\uD83D\uDE00` escapes is one character. A lone surrogate, as an escape or raw, is `E_COERCE` (RFC 8259 allows it, but no UTF-8 text can hold it). Raw control characters below U+0020 are `E_COERCE`. `stringify` escapes `"` `\` and the controls (`\b \f \n \r \t`, others as `\u00xx` in lower case), and writes every other character raw (`ensure_ascii=False`: `/`, U+007F, U+2028 and non-ASCII are not escaped). A byte order mark is not skipped: it is `E_COERCE` at offset 0.
- **Records.** `parse` keeps the keys in the order they were written (FL records keep insertion order, `keys` returns it, and `stringify` writes it; record equality ignores the order). A **repeated key is `E_COERCE`** with the position of the second one, not "last wins": the data would be lost silently, and parsers disagree about which one wins. The key `__proto__` and the empty key are ordinary keys. Record keys are always strings; a format with other keys (CBOR, YAML) must turn them into strings itself and decide what a collision means.
- **Bytes.** FL `bytes` have no JSON form: `stringify` of `bytes`, a quotation or a file, anywhere in the value, is `E_TYPE`. The caller chooses the text and puts it in a `str` first (`bytes>hex`, or the `base64` words), so a format never hides an encoding choice; say which one in the op's doc string.
- **Whole value.** The top-level value may be any JSON value (`42`, `"x"`, `null`), as in RFC 8259; surrounding white space (space, tab, LF, CR) is allowed, other white space (U+00A0, U+2028, a form feed) is not. Comments, trailing commas, single quotes, unquoted keys, `NaN`, `Infinity`, a leading `+`, `.5`, `1.` and leading zeros (`01`) are `E_COERCE`.
- **Errors.** A bad text is `E_COERCE` whose message ends `at offset N (line L, column C)` (offset and column count code points, lines and columns start at 1) and whose `detail` has `offset`, `line`, `column` and `reason`. Truncated text is `E_COERCE` at the end of the input. Nesting deeper than **512** levels is `E_LIMIT_VALUE` in `parse` and in `stringify` (checked on entering each container, so 100,000 `[` never exhausts the host stack). The size of a parsed value (the measure of LANGUAGE.md section 10.8) and the size of the text `stringify` writes are held to `ctx.limits.maxValueBytes` while they grow (`E_LIMIT_VALUE`), so a small text of many empty arrays cannot build a value beyond the limit.
- **Cost.** Both directions are one primitive call: a 64 KiB document (68,471 characters, 800 objects) parses in 2 VM steps and about 10 ms and stringifies compact or indented in 2 steps, against 358,523 steps for the bare FL loop over a 64 KiB text that was measured to justify the primitive (5.5 steps a character, before any state). The words that build or read the values (a `map` over a list of records) cost steps in the caller as usual.
- **Wiring.** An op that takes JSON text declares `data:str` (bytes are decoded as strict UTF-8 by the coercion), calls `json:parse`, and works on the value; an op that returns JSON declares `-- str` and ends in `json:stringify`, `json:compact` or `json:pretty`. Do not return an FL `list` or `record` from an op (they are not UI types). Give an `indent:int=2` parameter when the output is for people to read, as `csv:to-json` does (0 is compact).
- **Vectors.** The expected texts come from Python's `json` module (`json.dumps(v, indent=n, ensure_ascii=False)`, `separators=(",", ":")` for compact) and the examples of RFC 8259 section 13, never from CyberChef. `src/json.test.ts` is the model: it checks the values by shape (`int` as a bigint, `num` as a number, a record as its entries), the round trips, every error class, the depth limit at 512 and 513 and the 64 KiB cost.

### CSV (`csv:to-json`, `csv:from-json`)

`csv` is the first user of `json`, and the model for a data-format vocabulary: an FL op over the shared words and one or two private primitives for the per-character work (`csv:_parse` and `csv:_write`, justified in the primitives list above). Their category is `Data format`, the CyberChef group name (a new group for wave 7 data formats, to keep the CyberChef grouping). The delimiters are free text parameters as in CyberChef (`cell-delimiter` default `","`, `row-delimiter` default `"\\r\\n"` written as the two-character escapes); both read the escapes `\r \n \t \\ \xHH` so they can be typed in a text box, in `to-json` each character is a delimiter of its own (so the default row delimiter reads CRLF, LF and CR) and in `from-json` the text is written as it is. `to-json` has `format` (`array-of-dictionaries`, the default, or `array-of-arrays`) and an added `indent` (default 2). A 64 KiB CSV reads in 13 VM steps as arrays and about 53,000 as dictionaries (the header zip per row); 64 KiB of JSON writes as CSV in about 154,000 steps (about 12 per cell, so the default step limit allows around 800,000 cells).

## Running the vectors

Every op has vectors in `vocab/<v>.test.json`, and the catalogue test fails if an op has none. All 4,646 vectors (158 files) run through the in-process baker in Node as part of the worker package's tests:

```sh
npm test -w @forge/worker                              # includes test/vectors.test.ts
npx vitest run packages/worker/test/vectors.test.ts    # the vectors alone
```

The same vectors run in Chromium Web Workers, with and without cross-origin isolation:

```sh
npm run gate4:browser -w @forge/worker
```

Multi-step recipes that cross vocabularies (for example `text:split` into `text:join`) are tested in `packages/worker/test/phase4-recipes.test.ts`, because a single-op vector cannot feed a list into another op.

## The CyberChef coverage table

`docs/COVERAGE.md` is generated: it lists each of CyberChef's 506 operations (names only, in `docs/coverage/cyberchef.json`, grouped by CyberChef category) against the Forge words that cover it, or `redesigned` / `dropped` with a reason, or `not yet`. The data is one JSON file per area, `docs/coverage/<area>.json` (`encodings`, `classical`, `bits`, `text`, `regex`, `analysis`, `flow`, ...), an array of `{ "cyberchef", "status": "covered" | "redesigned" | "dropped", "forge": [...], "note" }` checked by `docs/coverage/coverage.schema.json`. `forge` lists catalogue words (`base64:decode`; an alias is written `classical:rot13`) and, for a structural recipe step that replaces an operation, `step:fork`, `step:subsection`, `step:if`, `step:repeat` or `step:comment`. `forge` is required for covered and redesigned, `note` for redesigned and dropped. Map only what exists; unmapped names show as `not yet`.

```sh
npm run coverage    # validate docs/coverage/*.json, then rewrite docs/COVERAGE.md (do not edit it by hand)
```

The part before the colon of a `forge` word is a lower-kebab-case vocabulary name (`quoted-printable:encode`). It fails if a `cyberchef` name is not in `cyberchef.json`, a name is mapped twice, or a `forge` word is not in the built catalogue. `src/coverage.test.ts` runs the same checks and **fails when `docs/COVERAGE.md` is out of date**. Every op WP adds or updates its own `docs/coverage/<area>.json`, so parallel WPs never edit the same file, and commits the regenerated `docs/COVERAGE.md`. A merge conflict in `docs/COVERAGE.md` is resolved by running `npm run coverage` again.
